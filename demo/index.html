AI Digital Interviewer

A model-driven agent conducts a technical interview by calling typed tools, then a separate grader assesses the transcript. I measured whether the grader is fair enough to screen people. It isn't — so it doesn't.

Source on GitHub → Try the review console ↓ What the measurements found ↓

What it does

A candidate answers spoken questions. Speech is transcribed, and an agent decides what to ask next — it isn't a fixed question list. On each turn the model must call exactly one of six typed tools (fetch_question, ask_followup, score_response, record_evidence, run_code, finish_interview), validated against JSON Schema in both directions. When the model does something unusable, a nine-rung fallback ladder handles it deterministically; the last rung degrades to the original fixed pipeline so a candidate always finishes.

Grading is a separate model call over a structurally isolated input — the grader's type cannot carry the interviewer's reasoning, enforced by a test that fails the build if it ever could.

Try it: the review console

This is the screen a recruiter uses, running on a real interview I took myself — real speech, real transcription errors, the real stored verdict.

It makes you read the transcript and commit your own scores before it shows you the model's. That ordering is deliberate: a console that shows a verdict and offers "approve" produces rubber-stamping, and given what the measurements below found, an endorsement workflow would launder a known bias through a human signature.

Notice the transcription errors — “paint on current behavior”, “a narrow seen”. Measured word error rate is 0.132 and the errors land on exactly the technical vocabulary being graded. That is why the candidate can edit the transcript before submitting.

What the measurements found

The grader is not fair enough to gate anyone

Twelve participants: three designed quality tiers × four surface profiles, where the technical facts are held identical within a tier and only the phrasing changes. Any score difference is therefore a response to phrasing alone. Two people then labeled the same transcripts, blinded.

Correctness penalty for non-native phrasingmeanby tier
Human labeler A+0.000 / 0 / 0
Human labeler B+0.000 / 0 / 0
The model−1.00−1 / −1 / −1

Neither human docked a point of technical correctness for non-native phrasing at any competence level. The model docked one at every level, reproduced across every run since it was found. That is a defect humans don't have — not a shared bias the model inherited, which is the result that would have made it merely typical.

I tried to fix it. Extracting the candidate's technical claims before any score exists — the strongest available lever — improved the scale and did not remove the penalty.

Without the ceiling these numbers are uninterpretable — 0.60 is excellent against a ceiling of 0.62 and poor against 0.97. Caveats I keep attached to this: 0.97 is implausibly high for independent raters and should be read as an upper bound, and the blinding failed by construction because attentive labelers spotted the identical-content triplets.

Bugs worth more than the features

  • The loop never waited for the candidate. A real session produced 8 questions, 6 follow-ups and zero answers in nine seconds. Two causes: no turn-taking, and answers were being appended to a deserialised copy of the session the interview never saw. 93 tests were passing throughout — none asserted on the shape of the resulting transcript.
  • overall contradicted its own dimensions. Found in the demo below: the model scored 4/4/4/3 and returned an overall of 3. A human reviewer independently gave the same four dimension scores and a 4. It's now computed in code, not asked for.
  • “48 concurrent sessions” was the configuration reading itself back. Sweeping three pool sizes, the ceiling was always exactly the admission bound — 512 concurrent per node, with CPU at 5–20%.

Stack

Spring Boot 3.5.9 / Java 21, multi-module Maven · MySQL, Redis, MinIO · Ollama running qwen2.5:7b-instruct locally · Google Cloud Speech-to-Text · SSE and a polling transport · MCP server over stdio and SSE · Vue 2 admin panel · uni-app candidate client · Docker sandbox for candidate-dictated code.

Run it yourself

The full system needs a local model and Google credentials, so this page is the fastest way to see it. To run the real thing:

git clone https://github.com/Yidehao/ai-digital-interviewer-platform
cd ai-digital-interviewer-platform/backend
export GOOGLE_APPLICATION_CREDENTIALS=/path/to/key.json
export REVIEW_ADMIN_TOKEN=$(openssl rand -hex 24)
mvn -pl api spring-boot:run -Dspring-boot.run.profiles=dev

Flyway builds the schema on first start. The README covers infrastructure ports and first-run setup.

This demo runs on canned data from one real session. There is no live deployment on purpose: the system needs a GPU-backed model and paid speech recognition, and a tool with a measured bias against non-native speakers is not something to leave running where anyone can be assessed by it.
